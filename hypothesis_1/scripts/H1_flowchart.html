Decisions locked in panel A

  • Block detection (your Q1). A block needs two annotations of the same code. Block i runs from onset of marker i to onset of marker i+1, and is kept only if that span is ≥ 59 s. Shorter spans are discarded and logged. Nothing is assumed about how many blocks survive.
  • Epoching order. Epochs are cut inside each block, then pooled per condition. No epoch straddles the seam between two blocks recorded minutes apart. With two 60 s blocks this gives 6 + 6 = 12 epochs per condition per session; the code never hard-codes 12.
  • AutoReject (your Q4). One fit per session file, ON and OFF together, so both conditions face identical thresholds.
  • 50% rule (your instruction). Applied to AutoReject drops only, evaluated on all four cells (pre-ON, pre-OFF, post-ON, post-OFF). Specparam drops are counted and logged separately and do not feed this rule (your Q5).
  • Both ROIs are always computed. The contralateral one is selected later, so the ipsilateral values stay in the file for any control analysis.

One consequence of the group z-score you should be aware of

  • Because the fit metric is z-scored across participants (your Q3), adding participant N+1 shifts the group mean and SD, so an epoch that survived at N = 22 can be dropped at N = 23. Every interim Bayes factor must therefore be computed on a full re-run of panel B over the current sample, not by appending one row to the previous table. The script does exactly this. The log records the group mean and SD of fit error at each N so the history is auditable.
  • Which metric is z-scored. "Poor model performance = z > 2" only works for a metric where higher is worse, so the z-score is applied to FOOOF's fit error. The r² is reported as the mean ± SD goodness-of-fit the protocol asks for, but is not the screening variable. Flag this if you intended otherwise.

Early stopping — scope limit (your Q6)

  • The protocol's rule terminates collection only when all four metrics cross a boundary. This pipeline produces metric 1 only. It therefore outputs the H1 Bayes factor trajectory and a per-N verdict (conclusive_H1 / inconclusive), and never issues a stop decision. The log states this explicitly so the interim record cannot be misread as a stop signal.
  • Two-sided for stopping, one-tailed for the main test. The protocol specifies two-sided interim tests but a directional confirmatory test. The script keeps these deliberately separate and labels both in the output.
  • Enrolment order. Sequential analysis needs the order participants were collected in. Folder-name sort (hx_01, hx_02, …) is used as the default. If your enrolment order differs from the numbering, add an order column to the contralaterality CSV and the script will use it.
